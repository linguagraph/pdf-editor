# W5.4: Select All of the whole document, and large copies in slices

Stage: W5 · Role: design Opus 5.5 · Branch: `phase-w-w5.4-large-copy` · Inputs: [W1.4](W1.4.md) §10, [plan](../plan.md) W5.4, [W5.4-reroute](W5.4-reroute.md) (merged in #524, §6 and question 1 leave this slice pending), `webapi/text.py`, `webapi/jobs.py`, `feedback/jobRun.ts`. Line numbers are for `main` at 0a4d847.

The reroute made Copy, Select All and Mark Text read the model selection (`TextSelection` over `PageTextIndex`). Two parts of W5.4 remain:

1. **Select All selects the whole document** under the Select tool, as the desktop's `DocumentView.select_all` does (`document_view.py:1062`: `{0,0}` to `{last, len(last)}`). Today it selects the page at the top.
2. **A large selection is copied in slices.** The engine's chunked `text.extract` does the work, with progress and Cancel. The main thread never builds the whole text from page indexes, and the engine worker is never busy for longer than one slice. The 50 MB limit (`MAX_COPY_CHARS`, `copy.tooLarge`) stays. It is now checked while the text arrives, not after.

Nothing changes under Hand. There, Select All is still the browser's range over the top page (reroute §5).

## 1. What exists already

It takes `start`, `end`, `cursor` and `budget_ms`, and gives `{text, cursor, pages_done, total, done}`. **Why not a job (`webapi/jobs.py`)?** A job runs on a *copy* of the document in the job worker. `jobs.prepare` copies the whole document, which can be hundreds of MB, before the first page is read. Jobs exist for work that can't be sliced, where a cancel has to kill a worker (decision 5). `text.extract` is already sliced and read-only, and it is cancelled between slices on the session worker. A slice costs at most about 100 ms of engine time, so the extract needs no copy and no worker restart, and Cancel works within one slice. Copy still uses the **job bar** (`jobProgress`) for progress and Cancel, through the `terminate` hook, as merge does. So the user sees the same bar as every other long task.

## 2. Select All of the whole document

### 2.1 Semantics

Under Select, Select All sets `TextSelection({page: 0, index: 0}, {page: last, index: len(last)})`, the desktop's selection. Under Hand, nothing changes. An empty document (no pages) does nothing.

### 2.2 Loading nothing but the last page

The selection needs exactly one number it may not have: the length of the last page's text (`PageTextIndex.length`, in code points). It does **not** need the other pages' indexes:

- **Drawing.** `SelectionMarks` draws a page only once that page's index has arrived (`SelectionMarks.tsx:16`). Mounted pages load their indexes as they scroll into view, which they already do. Pages that aren't mounted draw nothing and load nothing.
- **Copy.** Copy reads the covered indexes only when all of them are ready. Otherwise it goes to the engine (§3.1).

So Select All makes one `text.layer` request at most, for the last page, and only when that page's entry isn't cached (`textLayers.readyIndex(last, rev)`).

### 2.3 The loading state, and when the model is ready

The handle keeps one new ref, `selectAllPending: {page: number; revision: number} | null`.

1. If the last page's index is ready, set the selection at once. Nothing is pending.
2. Otherwise set `selectAllPending = {page: last, revision: revisionOf(last)}` and call `textLayers.index(last, rev)`. When it resolves, set the selection only if all of these still hold. In every case, clear the pending ref.
   - `selectingNow.current` is true;
   - `selectAllPending` is still the same object (no other Select All, drag or clear came in between);
   - `revisionOf(last)` is unchanged;
   - the page count is unchanged.
3. If the request fails, clear the pending ref and show `text.stillLoading`. Pressing Select All again retries, because a failed cache entry is forgotten.
4. A drag (`startPress`), `clearTextSelection`, leaving Select, or a revision change of any page clears `selectAllPending`.

**The model is ready** when `selectAllPending` is null and the selection is set. While Select All is pending, `copyPlan()` answers `pending` and Copy shows `text.stillLoading`. This is the only case left where Copy shows that message (§3.1).

### 2.4 The cache

The page index and text buffers stay as they are: `TextLayerCache` holds up to 300 entries (`MAX_TEXT_LAYERS`), filled by the pages in view. A whole-document selection adds the last page's entry and nothing else. Copy through the engine never fills the cache (§3.3). The text it reads lives only in the copy's own buffer until the clipboard write ends.

## 3. Copy in slices

### 3.1 Choosing the path

`DocumentViewHandle.selectedText(): ModelRead<string>` is replaced by `copyPlan(): CopyPlan`, in `text/copy.ts`:

```ts
export type CopyPlan =
  | { readonly kind: 'off' }                                // Hand or no view: the browser's selection
  | { readonly kind: 'pending' }                             // Select All waits for the last page's length
  | { readonly kind: 'local'; readonly text: string }        // every covered index is ready ('' = nothing)
  | { readonly kind: 'engine'; readonly start: TextPos; readonly end: TextPos; readonly pages: number };
```

`planCopy(selection, indexOf, pending)` is pure:

- `off` when not selecting;
- `pending` when Select All is pending;
- `local` with `''` for no selection or an empty one;
- `local` with `selection.text(indexes)` when `readModelIndexes` is `ready`. This is today's path, and it is synchronous. At most 300 pages can be ready, so the main-thread cost stays bounded: about 1 ms per 10 pages of string slicing;
- `engine` otherwise, with `pages = end.page - start.page + 1`.

This replaces Copy's `loading` branch (`copy.ts:82`) and its `loadPages` dependency. Copy no longer asks for up to 300 indexes to be loaded into the view's cache. It asks the engine for the text, which is cheaper, because `text.extract` returns text without char boxes. `readModelText` and `loadTextPages` stay for Mark Text (§6).

`copySelectedText` keeps its synchronous body for `off` and `local`. For `engine`, it calls `copyLarge(...)` (new file `text/largeCopy.ts`) **before it returns**, so the clipboard call is still made inside the keypress (§3.4).

### 3.2 The engine call

The existing `text.extract`, unchanged. No new Python, no DTO change, no `make_web_types` drift:

```ts
rpc.chunked('text.extract', { handle, start, end, budget_ms: COPY_BUDGET_MS }, { signal })
```

- `COPY_BUDGET_MS = 100`, the same as search. W1.4 §10 sets a slice at about 100 ms, so a render or a page click waits at most one slice. Pyodide runs one call at a time, so the slice is also the longest time the worker is busy. The "engine lock" in the worker is that serialisation: `extract` holds `session.lock` for one slice only.
- Slices are joined as the docstring says: a non-empty slice text is joined to the previous ones with `LINE_SEP`, and an empty slice adds nothing. That is the same rule as `TextSelection.text`, so the engine path and the local path give the same string (parity test, §9).
- Progress is `pages_done / total`, as the bar's percent.
- **Optional, not in this slice:** `extract` validates `start` and `end` against `cache.get(page)` on every slice (`text.py:73-74`), so it builds the first and last page's index once per slice. With 50 pages per slice that is at most 4% extra. Leave it as it is unless the measurement in §5 shows more than 10%. The fix would validate only when `cursor is None` (about 4 Python lines).

### 3.3 The runner (`text/largeCopy.ts`)

```ts
export async function runLargeCopy(deps: LargeCopyDeps, plan: EnginePlan, signal: AbortSignal):
  Promise<LargeCopyResult>   // { kind: 'text', parts } | 'tooLarge' | 'cancelled' | 'changed'
```

1. Keep `parts: string[]` and a running `length`, counting a `LINE_SEP` between non-empty slices.
2. For each slice: if `signal.aborted`, return `cancelled`. Push the text and add its length. If `length > MAX_COPY_CHARS`, **stop asking for slices** (abort the loop's own controller) and return `tooLarge`. Otherwise call `onProgress(pages_done, total)`.
3. `STALE_CURSOR` returns `changed`. An abort that comes with an error returns `cancelled`. Any other error is thrown and reported by `reportRpcError`.
4. `parts` go into the clipboard without first being joined into one string (§3.4).

`copyLarge` wraps it as a job on the bar:

- `jobProgress.begin({token: 'copy-<n>', label: t('copy.progress'), terminate: () => controller.abort()})`.
- **Bar delay.** The bar is shown only if the copy hasn't finished after `COPY_BAR_DELAY_MS = 300`, so a two-slice copy doesn't flash a bar. Before that, `begin` isn't called, and Cancel isn't needed yet.
- When `begin` returns false (another job's bar is up), refuse with `copy.busy` and start nothing (question 4). A second Copy while a copy runs is the same case. It is ignored, with no toast, because the running copy's token is the one on the bar.
- `finish(token, {ok: true, quiet: true})`, because Copy shows its own toasts: `copy.done`, `copy.tooLarge`, `copy.changed` or `copy.failed`. Cancel shows nothing, as for every job.

**Revision clear during a copy.** The copy captures `start` and `end` when it begins. A revision change on a covered page (Undo, Redo, an edit), or a page-count change, aborts the controller and gives `copy.changed`. The same subscription clears the selection (§4). So an edit made between two slices never mixes old and new text in one clipboard write. A new drag or Select All during the copy doesn't stop it. The copy is of what was selected when Copy was pressed, as on the desktop. Closing the tab aborts quietly.

### 3.4 Writing to the clipboard asynchronously

Firefox and Safari accept a clipboard write only inside the user's keypress or click, so the extract can't run first and call `writeText` afterwards. The design uses the async Clipboard API's own answer to this:

```ts
const blob = runLargeCopy(...).then(r => r.kind === 'text'
  ? new Blob(interleave(r.parts, LINE_SEP), { type: 'text/plain' })
  : Promise.reject(r));
navigator.clipboard.write([new ClipboardItem({ 'text/plain': blob })]);  // called inside the keypress
```

- `clipboard.write` is called synchronously in the keypress, with a **promise** for the data. The browser keeps the user activation for that write. This is the pattern Safari documents, and Chromium and Firefox (127 and later, with `ClipboardItem`) accept a promise value too. The e2e and manual checks in §9 confirm it on the pinned browsers.
- The `Blob` is built from `parts` with separators interleaved, so the whole text never exists as one JS string. Peak memory is the parts plus the Blob's UTF-8 copy (§5). The parts are dropped once the Blob exists.
- If the result is `tooLarge`, `changed` or `cancelled`, the data promise rejects. The write then fails and nothing reaches the clipboard (decision D4: never part of a selection). The runner's result decides the toast, not the write's rejection.

**Fallback (two presses).** This path is used when `ClipboardItem` or `clipboard.write` is missing, or when the write rejects with `NotAllowedError` after the text arrived. The runner's text is kept as `prepared = {key, parts}`, where `key` is the selection's start and end plus the covered revisions' signature. The toast `copy.ready` then gets an action, `copy.readyAction` ("Copy"). Pressing the toast's button, or Ctrl+C again with the same selection, is a new user gesture: it joins the parts and calls `writeText` synchronously. `prepared` is dropped when it is written, when the selection or a covered revision changes, or when the tab closes. So at most one prepared text (at most 50 MB) is held per tab.

### 3.5 The 50 MB limit and its message

`MAX_COPY_CHARS = 50 * 1024 * 1024` UTF-16 units, as today (`copy.ts:14`). The engine path checks it after each slice and stops as soon as it is passed. So the copy never reads more than the limit plus one slice, and the slices it never asked for are never read. The message is unchanged: `copy.tooLarge`, "The selection is too large to copy at once (about 50 MB of text). Select fewer pages." The local path keeps its existing check.

## 4. The revision clear, made O(changed pages)

Today's effect (`DocumentView.tsx:587-599`) loops from `start.page` to `end.page` on every render to snapshot revisions. With a whole-document selection on a 10,000-page file, that is 10,000 map writes per render (each scroll frame). The change:

- `RenderScheduler.subscribeRevisions(listener: (pages: readonly number[]) => void)`. `noteRevisions` passes the pages whose revision moved (`renderScheduler.ts:101`). Existing listeners ignore the argument.
- The view's listener clears the selection, `selectAllPending`, `prepared` and a running copy when any changed page is in `[start.page, end.page]`. That is O(changed pages), and `coveredRevisions` is deleted.
- A page-count change (insert, delete, reorder; `pageCount` at `DocumentView.tsx:900`) clears the selection too, because page numbers then no longer name the same pages. Today this only happens indirectly. It is checked in a test (§9).
- Undo, Redo or an edit therefore clears the selection, as it does now, and also cancels a running copy (§3.3) with `copy.changed`.

## 5. Memory and time budgets

| Measure | Budget | Basis |
|---|---|---|
| Engine time per slice | ≤ 100 ms + one page | `COPY_BUDGET_MS`. `extract` checks the budget after each whole page |
| Extract rate (Pyodide) | about 1.5–3 ms per text page | W0.2: 1.26 ms per page for search over `TextIndexCache`. Extract builds the same index, then slices it |
| 1,000 text pages (`large_1000.pdf`) | ≤ 4 s in Chromium, Cancel within 150 ms | Measured in the PR with `performance.now()` around `runLargeCopy`. Recorded, not a CI gate |
| Main thread per slice | < 5 ms | Pushing one string and updating the bar. No join, no index |
| JS memory, engine path | ≤ 2 × the text in UTF-16 (parts) + the Blob (≤ 1.5 × the text in UTF-8) | At the 50 MB cap: about 100 MB of parts, plus a Blob of 50–150 MB, briefly. The parts are released when the Blob is built |
| Worker memory | ≤ 50 pages of `PageTextIndex` at a time | `extract` makes a new `TextIndexCache` per call, freed with the slice |
| Select All | One `text.layer` call at most | §2.2 |

The memory warning (`feedback/memoryWarning.ts`) is not wired to Copy. The cap is what bounds Copy's memory.

## 6. Mark Text and other readers of the selection

- **Mark Text** over a whole-document selection would need every covered page's areas. Its `loading` path waits on `loadTextPages`, which is capped at `MAX_TEXT_LAYERS` (300). A selection over more than 300 pages therefore always ended in `text.stillLoading`, which is misleading. The change: when `end.page - start.page + 1 > MAX_TEXT_LAYERS`, Mark Text shows the new `redact.selectionTooLarge` ("Mark Text works on up to 300 pages at a time. Select fewer pages, or use Mark Pages.") and marks nothing. Marking a whole long document in slices is a separate follow-up (question 5).
- **Search and its highlight** don't read the selection. They are unchanged.
- **The desktop** is unchanged. Its copy is synchronous behind a wait cursor (`document_view.py:1052`). Applying the same slicing there is outside W5.4.

## 7. Keyboard and screen reader

- **Ctrl+A** stays bound to `select-all`. It is not handled when focus is in an editable field (the page box, the search box), where the field's own Select All applies. The existing dispatcher rule is unchanged, and a test checks it with the search box.
- **Announcement.** A whole-document selection is mostly off screen. After Select All, push an `info` toast, `text.selectedAll` (plural: "Selected the text of all {count} pages."). The toast region is the app's polite live region (`ToastRegion.tsx`), so screen readers hear it. A single-page document uses the `one` form. Hand's Select All doesn't announce, as today.
- **Progress.** The job bar is a `<progress>` with `aria-label` = `copy.progress`, and its Cancel button is reachable with Tab, as for every job. Focus isn't moved to the bar, so the user's place is kept. The result toast (`copy.done` and the others) is announced by the toast region.
- **Escape** isn't bound to cancel a copy. It already closes dialogs and panels, so Cancel is the bar's button.
- The hidden text spans that screen readers read (reroute, W1.4 §10) are unchanged. A whole-document selection doesn't add DOM for pages that aren't mounted.

## 12. Risks

- **Clipboard promise support.** If a pinned browser rejects a `ClipboardItem` whose data is a promise, or rejects one that takes several seconds to resolve, the copy falls back to the two-press path. It still works, at the cost of one more press. The manual check (§9.8) decides whether a browser goes straight to the fallback by feature test.
- **Focus loss during a long copy.** Chromium may reject a write that resolves after the tab has lost focus. The result is the fallback toast, not lost text, because `prepared` is kept.
- **Memory near the cap.** About 250 MB at peak on a 50 MB copy of non-ASCII text (§5). On a low-memory device that is risky, but it is the existing cap. Lowering it is question 3.
- **A pathological page.** One page with millions of chars makes one slice slow, because the budget is checked only between pages. This is the same as search. It isn't mitigated here.
- **Engine and local text disagree.** Both use the desktop's `TextSelection` rule, and the parity test (§9.6) pins the join. One known difference remains: the local path uses the index of the revision the user saw, the engine the current one. The revision abort (§3.3) makes these the same whenever the copy succeeds.
- **Select All's last page fails to load** (a damaged page). Select All then does nothing but show `text.stillLoading`. The desktop would raise, so this is no worse.
- **One job bar.** A copy can't run while an export or other job shows its bar (`copy.busy`). That is a limitation, not a fault.

## Questions for the maintainer

1. **Clipboard strategy: an async `ClipboardItem` write with a two-press fallback, or two presses always?** Recommended: `ClipboardItem` first, with the fallback. One press is what the desktop does, and the fallback costs about 30 lines.
2. **Path choice: local whenever every covered index is ready (up to 300 pages), or local only up to 20 pages as W1.4 §10 says?** Recommended: local whenever ready. It is synchronous (one press, plain `writeText`, works everywhere), and 300 cached pages slice in a few ms. The 20-page figure predates the cache.
3. **Keep the 50 MB limit?** Recommended: yes, unchanged. It is pinned by `copy.tooLarge` and the guide, and it bounds memory at about 250 MB. Revisit only if the manual check shows trouble on mobile.
4. **When another job's bar is up: refuse with `copy.busy`, or copy without a bar?** Recommended: refuse. A copy with no Cancel could run for tens of seconds with no feedback. Jobs are rare and finish.
5. **Mark Text over a selection of more than 300 pages: refuse (`redact.selectionTooLarge`), or mark in slices in this PR?** Recommended: refuse now. Marking text in engine slices needs a new read-only call that returns areas, and a single undo step over many slices, which is a larger design. Mark Pages covers the "redact everything" case.
6. **Announce Select All with a toast (`text.selectedAll`)?** Recommended: yes. Most of the selection is off screen, and the toast is the app's only live region, so both sighted and screen-reader users learn the scope.
7. **Validate `extract`'s positions only on the first slice (about 4 Python lines)?** Recommended: not now. The overhead is at most 4%. Revisit only if §5's measurement shows more than 10%.
