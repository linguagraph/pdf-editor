# W6.3b: Page-count probe, merged-result preview and source passwords in Combine

Stage: W6 · Role: design Opus 5.5 · Branch: `phase-w-w6.3b-probe-previews` · Inputs: [plan](../plan.md) (R6, W6.3), [W6.3a](W6.3a-combine-ranges.md) (page ranges; branch `phase-w-w6.3a-combine-ranges`, PR #531), [W6.3b progress](W6.3b-combine-progress.md), [W1.2](W1.2.md) sections 4, 10, 13 and 16, `src/pdfeditor/services/assembly.py` (`describe_source`, `merge`), `src/pdfeditor/webapi/jobs.py` (`_convert_merge`, `_run_merge`, `_range_pages`, `split_plan`), `src/pdfeditor/webapi/fonts.py` (`fonts.validate`, a call with no document), `src/pdfeditor/webapi/session.py` (`open_document` password codes), `src/pdfeditor/ui/combine/` (desktop), `web/app/src/combine/`, `web/app/src/organizer/insertFile.ts` (`PASSWORD_ATTEMPTS`), AGENTS.md (password rules).

This note designs what is left of W6.3 after W6.3a (page ranges) and the progress slice:

1. a **page-count probe**, so each PDF row shows its page count and a page past the end is marked on the right row before Combine runs;
2. a **preview of the merged result**: its page count and which pages of which source go where, without writing the merged file;
3. **password entry** for an encrypted source, on that source's row.

It is a design only. It builds on W6.3a, which must merge first: it reuses `pages/pageRanges.ts` (full mode), the `rangeError` outcome, the `combine.error.ranges.*` keys and the first pass of `_run_merge`.

## 1. What exists (after W6.3a)

- **Desktop.** `describe_source(engine, path, w, h, password)` returns `SourceInfo(page_count, locked, error, preview)` and never raises. The panel describes each file in a background job, shows `Password protected` rows, asks with `QInputDialog` (echo mode Password), keeps the password on the `CombineEntry` in memory only, and refuses to combine while a row is locked or unreadable ("Unlock 1 password-protected file, or remove it, to combine.").
- **Web dialog.** Knows names and sizes only. It never calls the engine worker; each Combine starts a fresh job worker (`startJobWorker`) and terminates it in `finally` (`run.ts`).
- **Web job.** `MergeSourceArgs(name, data, pages, ranges)` has no password. `_run_merge` opens ranged sources with `engine.open(path, None)` and maps `PasswordRequired` to `REFUSED` / `{reason: "encrypted_source"}`, naming no source. So an encrypted source cannot be combined on the web at all today.
- **Engine-worker calls with no document** exist: `fonts.validate` takes `{name, data}` (one `$bin`), checks the size before reading, holds no lock and stores nothing. The probe follows that shape.
- **Password codes** exist: `PASSWORD_REQUIRED` (none sent) and `WRONG_PASSWORD` (one sent, did not open), chosen by the caller because the engine raises one `PasswordRequired` for both (`session.open_document`). The app already translates both (`error.PASSWORD_REQUIRED`, `error.WRONG_PASSWORD`).
- **Attempt limit precedent.** Insert-from-file asks at most `PASSWORD_ATTEMPTS = 5` times (`organizer/insertFile.ts`, the same as `actions/pages.py _PASSWORD_ATTEMPTS`).

## 2. The probe call: `combine.probe`

Runs on the **engine worker** (already booted, no Pyodide start per file), in a new module `src/pdfeditor/webapi/combine.py`, registered in `METHODS` as `"combine.probe": Method(dto.CombineProbeParams, combine.probe)`, deadline class `action` (`scripts/make_web_types.py`), so `rpc/generated.ts` gains it on regeneration.

```python
@dataclass(frozen=True, slots=True)
class CombineProbeParams:
    name: str              # file name for messages and the suffix check; never a path; 1 to 255 chars
    data: bytes            # the whole file, one $bin buffer (at most limits.MAX_PROBE_BYTES)
    password: str | None = None  # used for this call only; never echoed, logged or kept

@dataclass(frozen=True, slots=True)
class CombineProbeResult:
    page_count: int        # >= 1
    encrypted: bool        # the file has an /Encrypt dictionary (with or without a user password)
    needed_password: bool  # it opened only with the password sent (so the row keeps that password)
```

**Order of checks** (each refusal stops the call):

| Step | Failure | Code | `details` |
|---|---|---|---|
| `name` length 1..255 | | `INVALID_ARGS` | `{path: "params.name"}` |
| suffix is `.pdf` (images are never probed, section 4) | | `INVALID_ARGS` | `{path: "params.name"}` |
| `password` not `None` and longer than 1,024 chars | | `INVALID_ARGS` | `{path: "params.password"}` (message names the field, never the value) |
| `len(data) > limits.MAX_PROBE_BYTES`, **before anything reads the bytes** | | `FILE_TOO_LARGE` | `{max_bytes, size}` |
| `engine.open(data, password)` raises `PasswordRequired`, `password is None` | | `PASSWORD_REQUIRED` | `{}` |
| same, `password` given | | `WRONG_PASSWORD` | `{}` |
| `OpenError` / `EngineError` (not a PDF, damaged) | | `OPEN_FAILED` | `{}` |
| `page_count == 0` | | `OPEN_FAILED` | `{pages: 0}` |
| anything else | | existing `failure_for` mapping (`OUT_OF_MEMORY`, `INTERNAL`) | |

`encrypted` is `document.info().encryption is not EncryptionMethod.NONE`, as `session._info` reads it. `needed_password` is `password is not None`: the client sends a password only after a `PASSWORD_REQUIRED` reply, so no second open is needed to tell. A file with only an owner password opens without one: `encrypted: true`, `needed_password: false`.

**The read-only rule.** The probe writes nothing and keeps nothing:

- It opens from **bytes**, never a path: no file in the worker's memory file system, unlike `_run_merge`.
- It touches no handle, no registry entry, no `DocumentSession`, no undo stack, no events (the call names no handle, so `CallRecorder` records nothing), no prepared job.
- `ENGINE_LOCK` is held only around `open`, `page_count`, the encryption read and `close` (in `finally`). The name, password-length and size checks run before the lock; the reply is built after it. No render, no outline read, no thumbnail.
- The `Document` is closed in `finally` on every path, including `PASSWORD_REQUIRED` (where nothing was opened) and an exception after open. No PyMuPDF object leaves the call.
- The password is a local argument, passed to `engine.open` once. It is never put in the result, an error message, `details` or a log record; `combine.py` has no logger call that takes params.

**The size limit: `MAX_PROBE_BYTES = 64 MiB`** (new, `limits.py`). The engine worker's wasm heap holds the open document too, and linear memory only grows (the `HEAP_WARN_BYTES` note), so probing a 900 MB file to count its pages would leave the viewer's heap 1 to 2 GB larger for the rest of the session. 64 MiB covers almost every file people combine; a larger PDF row shows "page count checked when combining" and the job (which has its own heap, discarded afterwards) remains the authority. The value is a question (Q2).

**Why the engine worker and not a job worker.** A job worker costs a Pyodide boot (seconds) and a second heap per probe; the engine worker answers in milliseconds for a normal file. The cost is that a probe waits behind, and briefly delays, render calls of an open document; the client runs one probe at a time (section 4) so the viewer is never starved.

## 3. Job changes: the password reaches the job that needs it

`MergeSourceArgs` gains `password: str | None = None` (PDF sources only).

`_convert_merge` (no document open yet):

- `password` on an image source: `INVALID_ARGS`, `{path: "args.sources[i].password"}`.
- `password` longer than 1,024 chars: `INVALID_ARGS`, same path. Messages never include the value.

`_run_merge`: W6.3a's first pass over ranged sources becomes a first pass over **every PDF source**, `_check_source(engine, path, password, ranges, index) -> list[int] | None`. It opens the source with its password, reads `page_count`, closes it, and resolves `ranges` (W6.3a rule) when given. `PasswordRequired` there becomes:

- `PASSWORD_REQUIRED`, `{path: "args.sources[i].password"}` when no password was sent;
- `WRONG_PASSWORD`, `{path: "args.sources[i].password"}` when one was.

`MergeSource(path, pages, password)` then carries the password into `merge()`, which already passes it to `engine.open`. The `REFUSED` / `encrypted_source` mapping around `merge()` stays only as a fallback that should never fire (every PDF was opened in the first pass). This replaces W6.3a's ranged-only pass, so a source is opened twice only once more than W6.3a already does for ranged sources (Q4).

The job worker holds the password only for this job: `runCombine` terminates the job worker in `finally` on success, failure and cancel, so nothing outlives the run. The output is a new, **unencrypted** document, as on the desktop (`merge()` builds it with `engine.new_document()`); the dialog says so (section 6) and the guide too.

`compare` keeps its `REFUSED` / `encrypted_source`; only merge changes code. W1.2 section 13 lists no merge arg fields, so it needs no edit. `PROTOCOL_VERSION` is not bumped (app and workers ship as one).

## 4. Client: probe queue and row state

New `web/app/src/combine/probe.ts`:

```ts
export type ProbeState =
  | { readonly kind: 'image' }                                  // never probed; 1 page
  | { readonly kind: 'pending' }                                // queued or in flight
  | { readonly kind: 'counted'; readonly pages: number; readonly encrypted: boolean; readonly unlocked: boolean }
  | { readonly kind: 'locked'; readonly attempts: number; readonly wrong: boolean }
  | { readonly kind: 'unreadable' }                             // OPEN_FAILED
  | { readonly kind: 'unchecked'; readonly reason: 'large' | 'engine' }; // FILE_TOO_LARGE, or the call failed
```

- **When.** A PDF row is probed once, when it is added, and again only when the user presses Unlock on it. Reordering, editing Pages and removing other rows never probe.
- **Queue.** One probe in flight at a time, in row order of addition. Bytes come from `file.arrayBuffer()` (a fresh copy) and are **transferred** to the engine worker, so the page side does not hold them twice. A file above the limit is marked `unchecked/large` without a call; the client constant `PROBE_MAX_BYTES` (64 MiB, in `probe.ts`) names `limits.MAX_PROBE_BYTES` in its comment, and a `FILE_TOO_LARGE` reply gives the same state, so a drift between the two only costs one call.
- **Engine.** The dialog gets the app's `EngineConnection` (prop `engine`, default the app connection) and waits on `whenReady()`. If the engine never comes up, rows stay `pending` until a probe fails, then `unchecked/engine`; Combine is never blocked by a missing count.
- **Stale replies.** Each result is applied by row `id`; a removed row's reply is dropped (the desktop's `uid` check). Closing the dialog clears the queue; a probe already in the engine finishes and its reply is ignored.
- **Mapping.** `PASSWORD_REQUIRED` → `locked {attempts: 0, wrong: false}`; `WRONG_PASSWORD` → `locked {attempts + 1, wrong: true}`; `OPEN_FAILED` → `unreadable`; `FILE_TOO_LARGE` → `unchecked/large`; any other error or a deadline → `unchecked/engine`. **No probe is ever retried automatically.**

The state lives in a `Map<number, ProbeState>` in dialog state, keyed by row id (not on `SourceItem`, which keeps its W6.3a shape), so the pure `sources.ts` helpers are unchanged.

**Blocking rules for Combine** (`checkSources` in `run.ts`, before any worker starts): a `locked` or `unreadable` row refuses the run with `combine.blocked.locked` / `combine.blocked.unreadable` (plural, desktop wording), focus on the first such row. `pending` and `unchecked` rows do not block.

**Inline out-of-range.** W6.3a checks Pages in syntax mode only. With a `counted` row, the blur and Combine-press checks run `parsePageRanges(text, pages)` in **full mode**, so `9` on a 5-page file is marked on its row at once with the existing `combine.error.ranges.outOfRange` message. Rows without a count keep syntax mode; the job stays the authority.

## 5. The merged-result preview

**Data source:** the probe counts and the Pages text, nothing else. New pure `web/app/src/combine/preview.ts`:

```ts
export interface PreviewRow { readonly id: number; readonly name: string; readonly take: number | null;   // pages this row adds; null = unknown
  readonly first: number | null; readonly last: number | null }                                         // 1-based result pages; null once anything before is unknown
export interface MergePreview { readonly rows: readonly PreviewRow[]; readonly total: number | null; readonly unknown: number }
export function mergePreview(items: readonly SourceItem[], probes: ReadonlyMap<number, ProbeState>): MergePreview;
```

- image row: `take = 1`; `counted` row: `take = parsePageRanges(pages, count).pages.length` (blank = `count`); a row whose Pages text has an error, or which is `pending`, `unchecked`, `locked` or `unreadable`: `take = null`.
- `first`/`last` run on in list order while every earlier row is known; `total` is the sum when every row is known, else `null`, with `unknown` = rows not counted.

**Why it writes nothing.** The page count and order of the result are fully determined by the per-source counts and the shared page-range rule (vector-checked against Python in W6.3a), so a merge would add no information while costing the whole merge (time, the job worker boot, a heap the size of the output) on every edit. The preview is recomputed synchronously on each change to the list, a Pages box or a probe state; it makes no call. Bookmarks are not previewed (Q5).

**UI.** Under the list, a `role="status"` summary (`aria-live="polite"`, updated on blur, not per keystroke):

- all known: `combine.preview.total` ("The combined file will have {count} pages.", plural);
- some unknown: `combine.preview.partial` ("{count} pages counted so far; {unknown} files are counted when you combine.", plural on `unknown`).

Each row shows, after its name, `combine.row.pages` ("{count} pages", plural) for `counted`, and, when known, `combine.row.placed` ("pages {first}–{last} of the result", or `combine.row.placedOne` for a single page). The source order written is the list order, so the rows themselves are the order preview; no second list is drawn.

## 6. Password entry on the row

A `locked` row replaces its Pages box with:

- `<input type="password">`, visible label `combine.password.label` ("Password"), accessible name `combine.password.labelFor` ("Password of {name}"), `autoComplete="off"`, `spellCheck={false}`, **uncontrolled** (the value is never in React state), not inside a `<form>` (so browsers do not offer to save it);
- a button `combine.password.unlock` ("Unlock"); Enter in the field does the same;
- a message line (linked by `aria-describedby`): `combine.password.needed` ("{name} is protected. Enter its password to use its pages. The password is not saved.") or, after a wrong one, `combine.password.wrong` ("That password is not correct. {left} tries left.", plural on `left`).

**Flow and retry rules.**

1. Unlock reads the field, **clears it at once**, and sends one `combine.probe` with `{name, data, password}`. One press is one send; nothing is resent on any failure.
2. `counted` (with `needed_password`): the password goes into the dialog's secret store (below) for that row id; the row shows its count and a lock icon with `combine.password.unlocked` ("Unlocked; the combined file has no password."). The Pages box returns.
3. `WRONG_PASSWORD`: attempts + 1, focus back in the empty field. **At most 5 wrong passwords per row** (`PASSWORD_ATTEMPTS`, imported from `organizer/insertFile.ts` so the app has one number). After the 5th, the field and Unlock are disabled and the row says `combine.password.gaveUp` ("Still locked. Remove the file, or add it again to try more passwords."). PDF files do not lock, so the limit protects nothing on the file's side; it keeps the behaviour the same as Insert from file and stops endless typo loops (Q3).
4. `unchecked/large` locked rows (known locked only from a job reply, section 7) cannot be probed: Unlock stores the password **unverified** and the row says `combine.password.unverified` ("The password is checked when you combine."). A wrong one comes back from the job and counts as an attempt.
5. Any other probe error after Unlock: the row stays `locked`, attempts unchanged, message `combine.password.notChecked` ("The password could not be checked. Try again."). Not retried automatically.

**Where the password lives, and when it is dropped.** W1.2 Q1 keeps open passwords out of JS state; Combine cannot follow that, because the job worker has no engine-worker session to borrow a password from. The exception is kept as narrow as possible:

- a `useRef<Map<number, string>>` in `CombineDialog` (not React state, not `SourceItem`, not the job store, not any storage, never rendered);
- read only by `runCombine` to build the job's args for rows whose probe said `needed_password` (or that were unlocked unverified); never sent for any other row, never sent to another call;
- deleted when the row is removed, when a job reply says that row's password is wrong or missing, and **all cleared** when the dialog closes or unmounts. A failed or cancelled job keeps them, so fixing a Pages box does not mean retyping.

**Never logged.** Nothing in `combine/` logs; the existing `console.*` calls in `engine/` and `rpc/` print messages, never params; `RpcError` messages from Python never carry the value (section 2); `JSON.stringify` of the job request holds it only as a transient string. Tests assert all of this (section 10).

## 7. Job replies on a row

`runCombine` recognises `PASSWORD_REQUIRED` / `WRONG_PASSWORD` with `details.path` matching `/^args\.sources\[(\d+)\]\.password$/` and returns a new outcome `{status: 'passwordError', index, wrong: boolean}`, finishing the job `quiet: true` (as W6.3a does for `rangeError`). The dialog sets that row to `locked` (attempts + 1 when `wrong`), drops its secret, and focuses its password field. This covers files above the probe limit, rows the engine could not probe, and a file that changed on disk between probe and Combine. The job's `out_of_range` replies keep W6.3a's path.

## 12. Risks

- **Heap growth on the engine worker.** Each probe copies up to 64 MiB into the viewer's heap, which never shrinks. The one-at-a-time queue bounds the peak at one file, but the high-water mark can still rise by about twice the largest probed file. The limit is the lever (Q2).
- **Viewer latency while probing.** A probe holds `ENGINE_LOCK` for one open (tens of ms for a normal file, longer for a damaged xref that MuPDF repairs). Render calls queue behind it. One probe at a time keeps this to a stutter, not a freeze.
- **Password in page memory.** The deviation from W1.2 Q1 is real: the string sits in a `Map` in a ref while the dialog is open, and in one transient request string. It is never rendered, stored, logged or sent anywhere but the probe and the job, and it dies with the dialog and the job worker. A page script with access to the heap could read it; the CSP (`'self'` only) is the defence, as for every typed password field.
- **Combined file loses protection.** Combining a protected file produces an unprotected one, on the desktop too. The row and the guide say so; adding encryption is W7.5's job (Encrypt on the result).
- **Owner-password-only files** open without a password, so their permission flags are not carried into the result (desktop parity). `encrypted: true` lets a later slice warn if wanted.
- **Changed W6.3a behaviour.** Merge's `REFUSED`/`encrypted_source` becomes `PASSWORD_REQUIRED`/`WRONG_PASSWORD` with a path. The app's `error.REFUSED.encryptedSource` is still used by compare; merge tests that expect `REFUSED` change.
- **Every PDF opened twice in the job** (first pass, then merge). Small next to the copy; W6.3a already accepted it for ranged sources.
- **Unverified passwords** for files above the probe limit are found wrong only after the job worker boots; the row then shows the error, and the attempt counts.

## Questions for the maintainer

1. **Accept the narrow exception to W1.2 Q1 (a source password held in a dialog ref until the dialog closes, and sent to the document-less job worker)?** Recommended: **yes**. The alternative is a probe that returns a decrypted copy of the source, so no password leaves the engine worker; but that writes a whole decrypted file, doubles the page-side memory per protected source, and keeps the decrypted bytes (worse than the password) in JS for longer. Sending the password with the job that needs it, then terminating that worker, exposes less.
2. **Probe size limit: 64 MiB?** Recommended: **yes**, 64 MiB. Raising it to `FILE_WARN_BYTES` (200 MiB) counts more files at the cost of a permanently larger viewer heap; a probe job worker (no limit, heap discarded) costs a Pyodide boot per dialog. Revisit with W8.3's memory numbers.
3. **Five wrong passwords per row, then remove or re-add?** Recommended: **yes**, the same `PASSWORD_ATTEMPTS` as Insert from file. PDFs have no lockout, so this is consistency, not protection; the desktop panel has no limit, and if you prefer parity with it, drop the counter (saves ~10 lines).
4. **Open every PDF source in the job's first pass (not only ranged ones), so password errors name their source?** Recommended: **yes**. Without it, a `PasswordRequired` from inside `merge()` cannot say which source failed, and the dialog could not put the field on the right row.
5. **Thumbnails of each source's first page and a bookmarks preview, as the desktop has?** Recommended: **not in W6.3b**. The plan asks for the page count and order; a thumbnail needs a render per source in the engine heap (a heavier probe), and the bookmarks preview needs each outline read. Tick W6.3 without them; list them as a follow-up if users ask.
6. **Call name `combine.probe`, or a generic `files.probe` that Insert from file could also use?** Recommended: **`combine.probe`** now. Insert from file runs its open inside an action already; a rename is a one-line change with `generated.ts` regeneration if a second user appears.
7. **Two PRs (probe and preview, then passwords) rather than one?** Recommended: **yes**. One PR would be ~470 lines, over the budget, and the password half deserves its own review against the AGENTS.md rules.
